# `sherpa plan` — stage 1: deterministic rules over the model

> Owner of: invocation, rules, file format, interpretation. Field semantics belong to the schema
> [`src/sherpa/schemas/harness-plan.schema.json`](../src/sherpa/schemas/harness-plan.schema.json) (v1); code in
> [`src/sherpa/plan/`](../src/sherpa/plan/) (`rules.py` rules, `yamlio.py` format). Principles: ADR-0006 (rank and
> floor), ADR-0011 (generators), ADR-0012 (units, visibility, decisions). Status: M2, v0.3.0.

## Invocation

```bash
sherpa plan <repo>                 # reads <repo>/.sherpa/codebase-model.json (scans when missing or stale)
sherpa plan <repo> --rescan        # rebuild the model
sherpa plan <repo> --no-fetch      # (re)scan without 'git fetch origin'
sherpa plan <repo> --out -         # YAML to stdout, console view to stderr
```

Output: `<repo>/.sherpa/harness-plan.yaml` (checked in, ADR-0005) plus the console view — `+` proposal, `-`
reasoned no, every criterion with ✓/✗, notes below. Exit 0 ok, 1 error (no repo, invalid plan file, unknown
`[plan]` key). Runtime with an existing model: milliseconds (a 15k-file model: 0.16 s including Python start-up).

Approval: set `decision: accept` or `reject` per entry in the file. Running `sherpa plan` again keeps decisions
you set via the key `(kind, target, scope)` and reports how many were kept.

## Units

Rules work on **units**: every module from T1 plus every depth-1 directory that no module covers
(`infrastructure/`, `pipelines/`), is not a dot directory and reaches `dir_min_files`. A root module covers
everything. Units are `module` or `dir`; both carry files, LOC, generator output, commits/90d, commits/30d,
authors/90d, dependents.

The **ranking** runs over business units (no test units, no generator-dominated ones). Quartile = rank ≤
⌈n · agent_top⌉; ties by id. It is in the plan header (`ranking`) so every "rank 7/44" can be recomputed.

## Rules

| Building block | `propose` when | No visible when |
|---|---|---|
| `outcome` | always, first — no harness without a signal (ADR-0008) | — |
| `owner-doc` | unit not dormant: ≥ 1 commit/90d **or** ≥ 1 dependent | always (the reader must know dormant units) |
| `agent` | rank ≤ quartile **and** commits/90d ≥ 20 **and** files ≥ 30 **and** authors/90d ≥ 2 | unit within reach: rank in the quartile or commit floor met; generator-dominated always |
| `librarian` | top 2 by commits/30d **and** (commits/30d ≥ 30 **or** commits/90d ≥ 80) | within reach: rank ≤ top N or one floor met; generator-dominated always |
| `test-infra` | the most active test unit has ≥ commits/90d of the most active business unit | always (one line) |
| `skill` | generator with ≥ 5 generated files; config alone only for families without detectable output (OpenAPI) | — (traces below the floor counted in a note) |

**Generator-dominated** (share of generator output ≥ `generated_share`, default 50 %): no agent, no librarian, no
rank — the skill for the generator instead. The owner doc stays. Example: a migrations project with 399 of 412
files generated was agent candidate number 8 under the old rules; now: "the knowledge lives in the generator — see
skill regenerate-ef-migrations".

**No's only within reach**: a module with 1 commit and 1 author gets no listed agent no — the information
"rank 37/44 ✗ · 1 commit ✗ · 4 files ✗ · 1 author ✗" helps nobody. Such units are counted in one `notes` line.
On a large monorepo that turns ~100 no's into ~16, each with met and unmet criteria side by side.

Every `reason` names what is missing and the flip criterion: `rank 2/2 churn, 1 authors. Flips when: rank ≤ 1
by commits/90d and authors/90d ≥ 2`.

Configuration in `<repo>/sherpa.toml`:

```toml
[plan]
agent_top = 0.25                   # top quartile by commits_90d
agent_min_commits_90d = 20
agent_min_files = 30
agent_min_authors_90d = 2
librarian_top_n = 2
librarian_min_commits_30d = 30
librarian_min_commits_90d = 80
dir_min_files = 10                 # a directory without a module counts as a unit from this many files
generated_share = 0.5              # from this share of generator output: skill instead of agent/librarian
skill_min_generated_files = 5
```

## File format

```yaml
# harness-plan — generated by sherpa 0.3.0 from origin/main@1a2b3c4d5e
sherpa: 0.3.0
schema_version: 1
repo: shop
model: {trunk: origin/main, rev: …, as_of: …, sherpa: 0.3.0}
thresholds: {agent_top: 0.25, …}           # effective values
ranking: {commits_90d: [pay, core, web], commits_30d: [pay, core, web]}
notes: ["1 dormant units without owner doc …"]
entries:
- kind: agent
  target: pay
  scope: svc/pay
  default: propose
  decision: null                           # accept | reject — the only field for humans
  evidence: {path: svc/pay, files: 40, generated_files: 6, commits_90d: 24, commits_30d: 24, authors_90d: 2, dependents: 1, rank_commits_90d: 1/4}
  checks:
  - rank 1/4 churn · rank ≤ 1 by commits/90d ✓
  - 24 commits/90d · commits/90d ≥ 20 ✓
  - 40 files · files ≥ 30 ✓
  - 2 authors · authors/90d ≥ 2 ✓
  cost: 1 agent with knowledge manifest, 1 eval catalogue from the graph
- kind: skill
  target: regenerate-django-migrations
  scope: svc/pay/pay/migrations
  default: propose
  decision: null
  evidence: {family: django-migrations, home: svc/pay/pay/migrations, generated_files: 6, sources: [svc/pay/pay/models.py], configs: [svc/pay/manage.py], command: python manage.py makemigrations, …}
  checks: [6 generated files, 1 configs · generated files ≥ 5 (or config when output is not detectable) ✓]
  cost: '1 SKILL file: source, config, regeneration command'
```

Fixed field order instead of sorted keys: byte-stable **and** readable. `evidence` on one line so a plan with 60
entries stays reviewable in a PR diff. Goldens: `tests/goldens/` (polyglot fixture and active fixture;
`SHERPA_UPDATE_GOLDENS=1 pytest tests/test_plan.py` refreshes them after an intended rule change).

## Decisions and why

1. **Rank and floor, both** (ADR-0006). Five modules: ⌈5 · 0.25⌉ = 2 agent ranks, but only with ≥ 20 commits;
   fifty modules: at most 13.
2. **Authors as a floor.** A module only one person touches needs no agent that explains it (CodeScene: knowledge
   distribution). The criterion makes bus-factor-1 modules visible without favouring them.
3. **Generated code is regenerated, not explained** (ADR-0011). The scanner detects generator families by path,
   the plan proposes the skill at the central place — with source, config and command as evidence.
4. **Skip dormant units visibly** (ADR-0012). Owner docs for adapters with 0 commits and 0 dependents are bloat;
   the reader still sees them as a no with a flip criterion.
5. **No's only within reach** (ADR-0012). Terraform shows everything because every resource is a decision; here
   a module with one commit is not. The count line keeps the balance honest.
6. **Decisions survive the re-plan** (ADR-0012). The plan is checked in; without keeping, every scan would erase
   the approval. Terraform does not need this (the plan is transient), Renovate solves it with a config file.
7. **Plan without a model scans by itself.** One command is enough; `--rescan` forces freshness, the plan header
   names the model rev, `status` (M3) reports drift between plan rev and trunk.

## Interpretation for `apply` (M3)

- `propose` + `decision: accept` → create; `propose` without a decision → ask interactively (dry run first,
  ADR-0008).
- `skip` with `decision: accept` is allowed — the human may overrule the rule; the plan documents it.
- `skill` entries: the template renders `evidence.command`, `sources`, `configs`; `home` is the location of the
  SKILL file.
- `test-infra` → owner doc under the test module plus librarian candidate in the next plan.
