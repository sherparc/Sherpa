# Sherpa — Plan

> **Datum:** 2026-09-16 · **Autor:** Claude (Opus 5) mit Andrei · **Stand:** v0.1.0, M1 (T0-Scanner) fertig
> **Vorlage:** ein produktives Claude-Code-Harness (.NET-Monorepo, ~120 Harness-Commits, 17 Agents, 5 Librarians,
> deterministischer Checker) und dessen Bewertung vom 2026-09-16 (Innovation 8/10, Stabilität 6/10). Sherpa nennt
> dieses Projekt nicht beim Namen: Sherpa ist ein generisches Produkt, das Referenz-Harness nur ein Datenpunkt.

## 0. Ziel in einem Satz

Sherpa steht **über** einem oder mehreren Repos, ingestiert die Codebase deterministisch, schlägt eine
Harness-Infrastruktur (Owner-Docs, Agents, Skills, Commands, Librarians, Evals, Outcome-Kanal) **mit
Evidenz und Kosten** vor und legt nach Freigabe genau das an — idempotent, mit State, ohne
Handarbeit zu überschreiben.

## 1. Nicht-Ziele (bewusst)

| Nicht-Ziel | Warum |
|---|---|
| Alles am Tag 1 anlegen | Bloat ist die gemessene Schwäche des Referenz-Harness (5 Fat-Agents, 4/17 ohne Manifest). Default ist `skip`. |
| LLM-Prosa als Owner-Doc | Plausibel-falsche Docs = Drift ab Tag 0. Owner-Doc = Skelett + Scanner-Fakten mit Anker; Prosa bleibt `unverified`. |
| Eigenes Agent-Framework | Sherpa erzeugt Claude-Code-Artefakte (`.claude/`), es führt keine Agents aus. |
| Web-App zuerst | CLI ist testbar, CI-fähig und von Claude Code selbst aufrufbar. Web = späterer Viewer. |
| Referenz-Harness als Testfall | Es ist das Template. Der Beweis muss auf **fremden** Repos gelingen. |

## 2. Architektur — drei Stufen, drei Artefakte

```
sherpa scan   ──► codebase-model.json    deterministisch, 0 LLM, Adapter je Sprache
sherpa plan   ──► harness-plan.yaml      Wissensarchitekt: LLM, aber nur gegen das Modell
sherpa apply  ──► .claude/** + sherpa-state.json   deterministisch, idempotent, Marker
sherpa status ──► Diff State ↔ Dateisystem, Drift-Report
```

Vorbilder aus der Industrie, die nachweislich funktionieren:

| Vorbild | Was Sherpa übernimmt |
|---|---|
| Terraform `plan`/`apply` + State | Vorschlag vor Wirkung; Re-Run = Diff, nie Überschreiben; State kennt jede erzeugte Datei |
| Backstage Catalog + Scaffolder | Owner pro Komponente; Templates mit Parametern |
| Tornhill Hotspots (Churn × Komplexität) | Drift-Proxy am Tag 0 aus `git log`, ohne Sync-Historie |
| Roslyn / tree-sitter Dependency-Graph | Modulgrenzen = Owner-Kandidaten; Code-Anker gratis (Checker-Regel: Anker existiert im Quellbaum) |
| `<auto-generated>`-Marker | generiert vs. handbearbeitet unterscheidbar; handbearbeitet wird nie überschrieben |
| Renovate/Dependabot | Librarian = kleiner, scoped Bot, der Änderungen vorschlägt statt direkt editiert |

### 2.1 Scanner → `codebase-model.json`

Deterministisch, testbar mit Fixture-Repos, **sprachunabhängig**. Drei Schichten, jede liefert ohne die nächste ein gültiges Modell:

| Schicht | Quelle | Gilt für | Liefert |
|---|---|---|---|
| **T0 Git** ✅ M1 | `git log`, `git ls-tree` gegen `origin/<trunk>` (ADR-0003) | jedes Repo | Churn, Hotspots, Autoren, Dateibaum, LOC, generierte Dateien — Details in `docs/scan.md` |
| **T1 Struktur** | Verzeichnis-Heuristik + Manifest-Dateien (`*.csproj`, `pyproject.toml`, `package.json`, `go.mod`, `Cargo.toml`, `pom.xml`, …) | jedes Repo mit Manifesten | Module, Deps zwischen Modulen, Test-Zuordnung |
| **T2 Sprache** | Adapter (`sherpa/adapters/<lang>/`), optional tree-sitter | pro Sprache, erste: `dotnet`, `python` | Symbole/Anker, feinere Deps |

Ein Repo ohne Adapter bekommt T0+T1 und damit Owner-Docs, Hotspots, Churn-Schwellen und Evals aus dem Graph —
nur Code-Anker (C7) fehlen. Der Adapter ist ein Plugin, kein Muss.

```json

  "modules": [                                                                         ← T1, geplant
```

### 2.2 Wissensarchitekt → `harness-plan.yaml`

Der einzige Ort mit LLM. Input: nur das Modell + Templates. Output: Vorschläge, **jeder** mit Evidenz,
Kosten und Default. Schwellwerte sind konfigurierbar, Startwerte aus der Analyse-Praxis des Referenz-Harness:

| Baustein | `propose` wenn | sonst |
|---|---|---|
| Owner-Doc | immer, je Modul | — |
| Agent | `commits_90d ≥ 40` **und** `files ≥ 30` | `skip` (Owner-Doc reicht) |
| Skill | Muster ≥ 2× im Code belegt (Scanner-Pattern-Katalog) | `skip` |
| Librarian | `commits_90d ≥ 100` **oder** `commits_30d ≥ 40`, kohärenter Bereich, max. 2 je Plan | `skip` mit Kippkriterium |
| Eval | für jeden Agent, automatisch aus dem Graph (§2.4) | — |
| Outcome-Kanal | immer, **zuerst** | — |

```yaml
- kind: librarian
  scope: src/Shop.Pricing/
  evidence: {commits_90d: 143, commits_30d: 51, hotspot_rank: 2}
  cost: "1 Scheduled Task, 1 SKILL, ~40 Anker"
  default: propose
- kind: agent
  scope: src/Shop.Reporting/
  evidence: {commits_90d: 12, files: 18}
  default: skip
  reason: "unter Schwelle; Owner-Doc reicht. Kippkriterium: commits_30d ≥ 20"
```

Modell-Anbindung (ADR-0004): Provider-Schnittstelle mit zwei Protokollen — OpenAI-kompatibel (vLLM lokal auf
`localhost:8000`, Ollama, OpenRouter, …) und Anthropic nativ. Konfig in `sherpa.yaml`:
`llm: {provider: openai, base_url: http://localhost:8000/v1, model: qwen3.8-flash-next}`. Jeder LLM-Output wird gegen
das Plan-JSON-Schema validiert; der Plan-Header trägt `model`, `prompt_hash`, `model_hash` — der Plan ist damit
nachvollziehbar, auch wenn das Modell nicht deterministisch ist.

Freigabe: interaktiv (`sherpa apply` fragt je Eintrag) oder als Datei-Edit (`default:` → `accept`/`reject`),
in Claude Code über `/sherpa-plan`.

### 2.3 Harnessing → `.claude/**` + `sherpa-state.json`

- Templates aus dem Referenz-Harness, **generischer Teil** (ADR-0002): Owner-Doc, Agent mit
  `knowledge:`-Manifest, SKILL, Command, Librarian-SKILL, Eval-Katalog, Hook-Set, Checker.
- Jede erzeugte Datei trägt Marker `<!-- sherpa:generated v0.1.0 hash=… -->`. Hash im State.
  Datei geändert (Hash ≠ State) → `apply` fasst sie nicht an, `status` meldet `hand-edited`.
- Checker (generischer Nachfolger des Referenz-Checkers) wird mit installiert; `apply` endet mit `0 FAIL`, sonst Rollback.
- Multi-Repo: ein `sherpa.yaml` im Workspace, ein State je Repo, Templates geteilt.
- **Determinismus-Garantie:** `apply` ist eine reine Funktion `(plan, templates, state) → Dateien`. Kein LLM, kein
  Netz, keine Uhrzeit im Dateiinhalt (Zeitstempel nur im State), sortierte Ausgabe, stabile Hashes. Test: zwei
  Läufe auf gleichem Input → byte-identischer Baum. Gleiches gilt für `scan` (bei gleichem `origin/<trunk>`-Rev)
  und `status`. Nur `plan` darf nicht-deterministisch sein, und auch dort nur der LLM-Anteil.

### 2.4 Auto-Evals aus dem Graph (der Teil, den es am Markt nicht gibt)

Golden-Fragen mit Ground-Truth aus `codebase-model.json`, keine LLM-Erfindung:

- „Welche Module hängen von `Shop.Core` ab?" → `dependents`
- „Wo liegen die Tests für `Shop.Pricing`?" → `tests`
- „Welche Klasse ist der Hotspot in Pricing?" → `hotspots[0]`

Jeder generierte Agent hat damit am Tag 0 ein verifizierbares Eval. Baseline wird im State gespeichert;
`status` meldet Regression.

### 2.5 Outcome-Kanal und Lernen

Wird vor allem anderen installiert (Befund im Referenz-Harness: 15/15 Ausführungen `unknown`). Label pro
Ausführung und `harness_rev`; Playbooks/Instincts (ECC-Muster) erst, wenn ≥ 30 gelabelte Ausführungen
vorliegen. Lernen ohne Signal ist ein Versprechen, keine Funktion.

## 4. Bewusst NICHT vorgeschlagen

- **Rust-Kern** — siehe ADR-0001; Kippkriterium dort.
- **Vektor-/Semantik-Suche im Scanner** — Graph + Churn reichen für Owner-Kandidaten; Semantik später, wenn M2 zeigt, dass Modulgrenzen falsch geraten werden.
- **Obsidian-Projektion** — spezifisch für das Referenz-Harness, Adapter-Kandidat nach M7.
- **GEPA/DSPy-Optimierung der Prompts** — erst wenn Evals (M4) und Outcome (M5) stabil laufen.
- **LangChain / LangGraph** — siehe ADR-0004: ein LLM-Aufruf mit Schema-Validierung braucht keine Graph-Runtime;
  Kippkriterium dort.

## 5. Teststrategie

Viele Tests, kleine Einheiten, alles reproduzierbar:

| Ebene | Was | Wie |
|---|---|---|
| Unit | jede Funktion in `src/sherpa/` | `pytest`, Fixture-Repos werden **programmatisch** gebaut (`tests/conftest.py`), feste Git-Daten/Autoren → gleiche SHAs |
| Determinismus | `scan`, `apply`, `status` | zwei Läufe, Baum-Hash-Vergleich |
| Snapshot | `codebase-model.json`, `harness-plan.yaml` je Fixture | eingecheckte Golden-Dateien, Diff bei Abweichung |
| Selftest | Checker (Muster: Selftest des Referenz-Checkers) | je Regel ein positiver und ein negativer Fall |
| Korpus | echte Repos unter `tests/corpus/` (ignored) | Smoke: Scan läuft durch, Schema valide, Laufzeit < 60 s |
| Schema | `codebase-model`, `harness-plan`, `sherpa-state` | JSON-Schema unter `src/sherpa/schemas/`; Validierung in Tests immer, zur Laufzeit wenn `jsonschema` installiert (dev-Extra) |

Gate: Coverage ≥ 90 % für `src/sherpa/`, `pytest -q` grün vor jedem Meilenstein. Stand M1: 58 Tests, 98 %.
